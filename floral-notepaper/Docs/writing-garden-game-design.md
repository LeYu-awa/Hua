# 写作花园养成小游戏设计文档

## 1. 功能定位

“写作花园”是文本编辑器内置的轻量养成小游戏。用户通过真实写作获得资源，用资源培育植物、购置升级、扩建花园并解锁内容。系统的目标不是制造额外负担，而是把写作过程转化为可持续、可回访、可收藏的成长体验。

一句话定义：

> 用户通过写作获得动态资源，培育自己的主花园；每篇文档也会长出独立花盆，记录它从草稿到成熟、从沉淀到被重新回访的过程。

核心原则：

- 写作是主要输入，花园是正向反馈。
- 不因正常转移写作重心而惩罚用户。
- 奖励应鼓励持续创作、完善文档和回访旧知识。
- 文档花盆主要记录和展示单篇文档成长，默认不消耗主花园资源。
- 花园同时承担统计仪表盘功能，让用户看到自己的长期写作痕迹。
- 游戏机制要轻，不干扰编辑器的核心写作体验。

## 2. 核心循环

```text
写作行为
→ 获得动态资源
→ 培育植物、购置升级、扩建花园
→ 解锁植物、装饰、剧情、图鉴等内容
→ 文档花盆记录单篇文档成长
→ 回访旧文档获得奖励
→ 继续写作
```

系统分为两套互相连接但职责不同的养成结构：

| 模块   | 职责                         |
| ---- | -------------------------- |
| 主花园  | 承载长期养成、资源消耗、植物培育、装饰升级、内容解锁 |
| 文档花盆 | 承载单篇文档的写作程度、成熟状态、回访奖励和成长纪念 |

主花园负责游戏进度，文档花盆负责写作记忆。

## 3. 主花园系统

### 3.1 主花园目标

主花园是用户长期写作成果的可视化空间。它应该提供明确但不重压的成长目标，让用户愿意继续写作、整理和回访文档。

主花园可以包含：

- 植物种植与成长
- 花园地块扩建
- 花盆、道路、灯具、背景等装饰
- 植物图鉴
- 成就与收藏
- 写作统计面板
- 轻剧情或园丁日志
- 特殊主题区域，例如日记花圃、知识树、项目温室

### 3.2 主花园玩法

用户通过写作获得资源，再使用资源完成养成行为。

常见行为包括：

- 给植物浇水
- 提供阳光或养分
- 升级花盆
- 解锁新地块
- 购买装饰
- 培育新种子
- 触发植物进化
- 解锁花园剧情或图鉴条目

### 3.3 主花园反馈

主花园应提供短周期和长周期反馈。

短周期反馈：

- 写作后获得资源
- 植物轻微变化
- 花盆状态提升
- 当日任务完成提示

长周期反馈：

- 植物阶段进化
- 新区域解锁
- 主题植物收集
- 文档成熟后生成纪念植物或种子
- 多篇文档形成花簇、树丛或主题区域

### 3.4 主花园统计

主花园应具备全局统计功能，作为用户长期写作行为的仪表盘。统计信息不只是冷数据，也可以转化为花园中的纪念物、里程碑或成就。

建议统计项：

| 统计项     | 说明                             |
| ------- | ------------------------------ |
| 总键盘敲击次数 | 用户在编辑器内累计输入的按键次数               |
| 总写作字数   | 累计新增字数，可区分净增长和总输入              |
| 总删除字数   | 用户删除或重写的内容量，用于体现修改劳动           |
| 总活跃写作时长 | 过滤无操作时间后的实际写作时长                |
| 写作天数    | 有有效写作行为的自然日数量                  |
| 连续写作天数  | 当前连续写作天数，可只影响主花园轻奖励            |
| 完成文档数   | 被用户标记完成、发布或归档的文档数量             |
| 回访旧文档次数 | 触发回访行为的次数                      |
| 最常用按键排行 | 统计用户最常敲击的按键，例如空格、回车、退格、常用字母或符号 |

最常用按键排行可以做成轻量趣味展示，例如“键盘足迹”“今日最忙按键”“年度按键植物”。但需要注意隐私边界：默认只统计按键类型和次数，不记录完整输入内容，也不还原用户文本。

## 4. 文档花盆系统

### 4.1 文档花盆定位

每篇文档可以拥有一个独立花盆。该花盆在打开对应文档时显示，也可以在主花园的子菜单中集中展示。它用于表达该文档的写作程度、完善状态和历史价值。

文档花盆不是打卡惩罚系统。文档长时间未打开并不等于断更，因为当一篇文档完善后，用户自然会把精力转移到下一篇文档。

文档花盆的核心价值：

- 展示单篇文档从草稿到成熟的过程
- 鼓励用户完善文档
- 鼓励用户回访旧文档
- 把文档生命周期变成可见的养成痕迹
- 展示该文档自己的写作统计信息
- 作为记录型成长物，而不是资源消耗型负担
- 允许用户通过种子解锁和更换文档花盆中的植物

### 4.2 花盆展示位置

文档花盆可以出现在两个位置：

| 位置    | 展示内容                |
| ----- | ------------------- |
| 文档编辑页 | 当前文档的花盆状态、成长阶段、近期反馈 |
| 花园子菜单 | 所有文档花盆列表、筛选、排序、回访建议 |

编辑页中的花盆应保持轻量，不遮挡写作。可以采用侧边小组件、顶部状态、悬浮角标或可折叠面板。

### 4.3 文档花盆状态

建议状态如下：

| 状态   | 含义                  | 是否负面 |
| ---- | ------------------- | ---- |
| 生长期  | 文档仍在持续创作或修改         | 否    |
| 成熟期  | 文档已经比较完整            | 否    |
| 静养期  | 文档较久未打开，但被认为已经沉淀    | 否    |
| 回访期  | 用户重新打开较久未访问的文档      | 否    |
| 再生长期 | 用户对旧文档进行了有效修改、扩写或重构 | 否    |

不建议使用“枯萎”“死亡”“濒危”等强惩罚表达。文档花盆的语气应更接近保存、沉淀、重逢和再生。

示例文案：

- “这盆花正在安静地保存你的想法。”
- “它已经成熟，暂时不需要频繁照料。”
- “你回来时，它认出了你。”
- “旧枝上长出了新的叶片。”

### 4.4 文档花盆统计

每个文档花盆应展示该文档自己的统计信息，用于表达这篇文档被书写、修改、回访和沉淀的过程。

建议统计项：

| 统计项       | 说明                 |
| --------- | ------------------ |
| 本文档键盘敲击次数 | 用户在该文档内累计输入的按键次数   |
| 本文档字数     | 当前文档字数             |
| 累计新增字数    | 包含后续被删除的历史输入量      |
| 累计删除字数    | 体现重写、删改和整理工作       |
| 有效编辑次数    | 发生有效修改的次数          |
| 活跃编辑时长    | 该文档内的实际写作时长        |
| 首次创建时间    | 文档作为种子出现的时间        |
| 最近打开时间    | 最近一次回到该文档的时间       |
| 最近有效修改时间  | 最近一次产生有效编辑的时间      |
| 回访次数      | 间隔较久后重新打开、阅读或编辑的次数 |
| 被引用次数     | 其他文档链接或引用该文档的次数    |
| 完善度       | AI 或规则判断出的文档成熟程度   |

文档花盆中的统计应偏向“这篇文章经历了什么”，而不是只显示产出结果。删除、修改、重写都应被视为有效劳动。

### 4.5 花盆资源消耗原则

文档花盆默认不消耗主花园资源。用户开启大量新文档时，系统不应因此造成主花园资源匮乏，否则会反向抑制写作和探索。

推荐规则：

- 新文档自动生成基础花盆，不需要消耗资源。
- 文档花盆的自然成长由该文档的写作、修改、阅读和回访驱动。
- 文档花盆的基础状态、统计展示和成熟记录不消耗主花园资源。
- 只有用户主动为某个文档花盆购买装饰、皮肤、特殊盆器或纪念牌时，才可以少量消耗主花园资源。
- 文档成熟、回访、被引用时应更多产生收益，而不是产生维护成本。

花盆与主花园的关系应是：

```text
文档花盆记录成长与产出收益
主花园承接收益并提供长期养成目标
```

### 4.6 默认花盆与植物

系统应为文档花盆设置默认花盆和默认植物。用户创建新文档后，系统自动生成一个基础花盆，并优先种下默认植物。这样新文档从一开始就拥有可见的成长对象，但不会产生额外资源压力。

推荐规则：

- 新文档自动创建默认花盆。
- 新文档优先种下默认植物。
- 默认花盆和默认植物不消耗资源。
- 默认植物也可以正常成长、成熟和产出奖励。
- 用户可以在设置中选择自己偏好的默认花盆和默认植物。

默认植物的设计应偏通用，例如“初心芽”“纸页草”“墨点苗”等，避免让用户在开新文档时必须先做选择。

### 4.7 特定植物解锁与更换

除默认植物外，用户可以消耗特定种子，为某篇文档花盆种下特定植物。特定植物可以代表不同写作主题、文档类型或用户偏好。

示例：

| 植物  | 适合文档         | 解锁资源  |
| --- | ------------ | ----- |
| 书页蕨 | 读书笔记、资料整理    | 书页蕨种子 |
| 年轮木 | 复盘、年度总结、长期项目 | 年轮木种子 |
| 夜藤  | 小说、故事、剧本     | 夜藤种子  |
| 银叶树 | 技术文档、方案设计    | 银叶树种子 |
| 晨露草 | 日记、随笔、灵感记录   | 晨露草种子 |

用户后期想更换花盆植物时，系统应允许更换，但需要消耗目标植物对应的种子。更换时建议保留文档花盆的总体成长记录，避免用户因为换植物而失去对该文档的历史沉淀。

推荐规则：

- 更换植物需要消耗目标植物的种子。
- 更换后保留文档花盆的文档统计、历史记录、回访次数和成熟记录。
- 更换后可以保留植物成长进度，并映射到新植物的对应阶段。
- 如果新植物拥有特殊成长线，可从当前成长阶段继续，而不是从零开始。
- 用户主动重置成熟植物时，才会清空该植物本轮成长进度。

这里的“保留成长进度”指保留文档花盆对该文档的成长认可，而不是简单复制植物外观。视觉上可以表现为新植物继承同等阶段，例如从幼苗、成株、开花或成熟阶段继续。

### 4.8 成熟植物重置与返还

当文档花盆中的植物成熟后，用户可以选择“采收”或“重置”该植物。重置会清空该植物本轮成长进度，但保留文档花盆的历史统计和成熟记录，并给予用户奖励。

成熟重置的目标是让已经完成一轮成长的文档继续参与养成循环，而不是停在终点。它适合已完成、已发布、已归档或阶段性成熟的文档。

推荐奖励：

- 必定获得该植物对应的种子。
- 获得其他随机资源，例如水滴、阳光、土壤、灵感、花粉。
- 有概率获得该植物相关装饰、纪念牌或图鉴进度。
- 如果该文档完善度高、被多次回访或被多篇文档引用，可提高额外奖励质量。

推荐限制：

- 只有成熟植物可以重置。
- 重置前需要用户确认。
- 重置只影响当前植物本轮成长，不删除文档统计。
- 重置后可以重新种下默认植物，也可以消耗种子种下其他植物。
- 同一文档短期内不应重复触发高额成熟奖励，避免刷资源。

成熟重置后的体验可以理解为：

```text
一篇文档完成了一轮生长
→ 用户采收成熟植物
→ 获得该植物种子和随机资源
→ 文档花盆保留历史
→ 用户可以开始新一轮植物养成
```

## 5. 文档完善度与 AI 判断

### 5.1 AI 的职责

AI 可用于判断文档是否足够完善，从而决定是否需要继续鼓励用户回到该文档。但 AI 不应直接惩罚用户，也不应覆盖用户对作品的主观判断。

AI 的职责是：

- 评估文档完成度
- 判断文档是否仍像草稿
- 判断文档是否已经适合进入成熟或静养状态
- 给出轻量的完善建议
- 辅助决定是否启用“待完善提醒”

### 5.2 判断维度

AI 可以参考以下维度：

| 维度    | 说明                  |
| ----- | ------------------- |
| 结构完整度 | 是否有标题、段落、层级、开头、结尾   |
| 内容密度  | 是否只是提纲、碎片，还是已经展开    |
| 主题一致性 | 内容是否围绕主要主题展开        |
| 完成信号  | 是否有总结、结论、发布、归档、完成标记 |
| 修改趋势  | 最近是否仍在频繁修改          |
| 用户意图  | 用户是否手动标记完成、归档或发布    |

### 5.3 用户判断优先

用户手动标记应优先于 AI 判断。

例如：

- 用户标记“已完成”后，文档默认进入成熟期。
- AI 可以提示“这篇文章仍有可完善空间”，但不能强制回到生长期。
- 用户可以关闭单篇文档的提醒。
- 用户可以将某篇文档设为“存档”，使其进入静养期。

## 6. 回访旧文档奖励

### 6.1 设计目标

回访奖励用于鼓励用户重新阅读、复习、引用和更新旧文档。它适合知识管理类写作工具，因为旧文档的价值往往来自再次连接和再次使用。

奖励可以命名为：

- 花盆的感激
- 旧枝新芽
- 回访露珠
- 记忆花粉
- 归巢奖励

### 6.2 触发条件

建议触发条件：

| 条件                  | 奖励       |
| ------------------- | -------- |
| 文档 7 天未打开后再次打开      | 小额回访奖励   |
| 文档 30 天未打开后阅读超过一定时长 | 中额回访奖励   |
| 旧文档被有效修改或扩写         | 额外奖励     |
| 旧文档被引用、链接或加入新项目     | 花粉类奖励    |
| 成熟文档被重新整理           | 复习或沉淀类奖励 |

### 6.3 防刷规则

为了避免用户反复打开文档刷奖励，需要限制触发频率：

- 每天最多触发有限次数，例如 3 次。
- 同一文档触发后进入冷却，例如 7 天。
- 打开时间过短不触发奖励。
- 单纯打开的奖励低于阅读、编辑、引用和整理。
- 可以根据用户历史行为动态降低疑似刷奖励行为的收益。

## 7. 资源系统

### 7.1 资源定位

资源用于培育主花园、升级设施和解锁内容。资源获取不应与具体操作类型强绑定，例如“写字只能给水滴”“修改只能给土壤”。系统应根据用户当前资源结构动态调整掉落倾向。

这套机制类似游戏中的动态难度调整，但更准确地说是“动态资源补偿系统”。

文档花盆不应成为主花园资源的持续消耗项。主花园资源主要用于主花园植物、设施、地块、装饰和内容解锁；文档花盆主要由文档行为驱动成长。这样用户大量开启新文档时不会被资源系统惩罚。

### 7.2 资源类型示例

| 资源 | 用途              |
| -- | --------------- |
| 水滴 | 植物基础成长、维持活力     |
| 阳光 | 加速成长、触发开花       |
| 土壤 | 升级花盆、扩建地块       |
| 灵感 | 解锁植物、剧情、主题内容    |
| 花粉 | 回访旧文档、建立链接、知识复习 |
| 种子 | 新植物、新项目、文档成熟奖励  |

资源类型不宜过多。P0 阶段建议控制在 2 到 3 种，例如水滴、阳光、土壤。后续再加入灵感、花粉和种子。

种子是一类特殊资源。它既可以用于主花园的新植物，也可以用于文档花盆的特定植物解锁和后期更换。默认植物不需要种子，但特定植物需要对应种子。成熟植物重置时，必定返还该植物对应的种子，以保证用户不会因为尝试更换或重置而永久损失核心收集进度。

### 7.3 动态掉落原则

资源掉落由以下部分组成：

```text
基础奖励
+ 缺口倾斜
+ 随机浮动
+ 保底修正
- 防刷衰减
```

设计原则：

- 用户当前最缺的资源拥有更高掉落权重。
- 如果用户卡在某个升级材料，应适度提高该材料掉落概率。
- 保留一定随机性，让奖励有惊喜。
- 如果某资源连续多次未掉落，应提高保底概率。
- 如果用户短时间内重复低质量操作，应降低收益。

### 7.4 掉落权重示例

```ts
type ResourceType = 'water' | 'sunlight' | 'soil' | 'inspiration' | 'pollen' | 'seed';

interface ResourceState {
  type: ResourceType;
  currentAmount: number;
  targetAmount: number;
  recentDropCount: number;
}

interface ResourceDropContext {
  resources: ResourceState[];
  activeUpgradeNeeds: Partial<Record<ResourceType, number>>;
  dailyRewardFactor: number;
  antiFarmFactor: number;
  randomFactor: number;
}
```

示例逻辑：

```text
如果水滴低于目标库存 20%，提高水滴权重。
如果用户正在升级花盆且缺少土壤，提高土壤权重。
如果花粉近期掉落过少，提高花粉保底概率。
保留 10% 到 20% 的随机权重，不让结果完全可预测。
```

## 8. 写作行为输入

系统需要记录用户的写作行为，但不应鼓励无意义灌水。建议将写作事件抽象成通用事件流，主花园和文档花盆都从该事件流中读取数据。

```ts
type WritingActionType =
  | 'write'
  | 'edit'
  | 'review'
  | 'link'
  | 'finish'
  | 'archive';

interface WritingEvent {
  documentId: string;
  timestamp: string;
  keypressCount: number;
  keyCounts?: Partial<Record<string, number>>;
  charsAdded: number;
  charsDeleted: number;
  activeSeconds: number;
  actionType: WritingActionType;
}
```

奖励计算不应只看字数，也可以参考：

- 活跃写作时长
- 键盘敲击次数
- 有效新增内容
- 有效修改内容
- 文档结构变化
- 文档之间的引用关系
- 是否完成或归档文档
- 是否回访旧文档

对于按键统计，系统应优先记录聚合数据，例如总敲击次数和按键计数表，而不是记录原始输入序列。这样既能支持“最常用按键排行”等趣味统计，也能降低隐私风险。

```ts
interface GardenWritingStats {
  keypressCountTotal: number;
  keyCounts: Partial<Record<string, number>>;
  charsAddedTotal: number;
  charsDeletedTotal: number;
  activeSecondsTotal: number;
  writingDaysTotal: number;
  currentWritingStreakDays: number;
  completedDocumentCount: number;
  revisitedDocumentCount: number;
}
```

## 9. 惩罚与提醒策略

### 9.1 主花园可以有轻度断更反馈

主花园可以对整体写作习惯提供轻量反馈，例如植物成长速度变慢、进入休眠、今日没有获得资源等。但不建议使用强惩罚。

推荐：

- 休眠
- 暂停成长
- 活力降低
- 回归后恢复
- 复苏奖励

不推荐：

- 植物死亡
- 清空连续天数
- 扣除大量资源
- 强提醒羞辱用户

### 9.2 文档花盆默认不启用断更惩罚

文档花盆不应因为长期未打开而惩罚用户。只有当 AI 判断文档仍明显不完整，并且用户没有标记完成或归档时，才可以启用温和的“待完善提醒”。

待完善提醒应满足：

- 可关闭
- 不扣奖励
- 不降低花盆等级
- 不破坏已有成长记录
- 只提示“值得回来看看”，不指责用户

## 10. 解锁内容

解锁内容是长期留存的关键。解锁内容应让用户产生“继续养”和“继续写”的期待。

可解锁内容包括：

- 新植物
- 新花盆
- 花园装饰
- 特殊地块
- 文档纪念牌
- 主题植物图鉴
- 园丁日志
- 写作里程碑
- 项目专属植物

示例：

| 写作行为     | 解锁方向     |
| -------- | -------- |
| 完成一篇长文   | 获得一颗种子   |
| 连续多日写作   | 解锁成长加速设施 |
| 回访旧文档    | 解锁花粉类装饰  |
| 多篇文档互相链接 | 形成花簇或藤蔓  |
| 某个主题持续写作 | 解锁主题植物   |

## 11. P0 版本建议

P0 阶段应尽量小，但要形成完整闭环。

建议功能：

| 模块    | P0 内容                   |
| ----- | ----------------------- |
| 写作事件  | 记录文档字数变化、活跃时长、打开时间      |
| 资源掉落  | 提供 2 到 3 种基础资源，并支持动态倾斜  |
| 主花园   | 一块地、一株植物、基础成长阶段         |
| 主花园统计 | 展示总键盘敲击次数、总字数、写作天数等基础统计 |
| 文档花盆  | 每篇文档一个花盆，显示成长程度         |
| 花盆统计  | 展示单篇文档字数、敲击次数、编辑时长和最近回访 |
| 默认植物  | 新文档自动生成默认花盆和默认植物，不消耗资源  |
| 种子机制  | 支持用特定种子解锁或更换文档花盆植物      |
| 成熟重置  | 成熟植物可重置，并返还该植物种子和随机资源   |
| 回访奖励  | 支持旧文档回访奖励和每日次数限制        |
| 花盆状态  | 支持生长期、成熟期、静养期           |
| AI 判断 | 先做可选的文档完善度判断，不参与惩罚      |

P0 核心闭环：

```text
写作
→ 获得动态资源
→ 培育主花园植物
→ 当前文档花盆成长
→ 回访旧文档获得小奖励
```

## 13. 风险与注意事项

### 13.1 避免写作变成刷资源

系统应奖励有效写作，而不是纯字数堆叠。需要结合活跃时长、编辑质量、文档结构和防刷规则。

### 13.2 避免惩罚创作节奏

写作者天然会在多个文档之间移动。文档长期未打开不代表失败。系统要尊重“完成、沉淀、转移重心”这些正常行为。

### 13.3 避免 AI 过度干预

AI 应辅助判断和建议，而不是替用户定义作品是否完成。用户标记完成、归档和关闭提醒的权力必须保留。

### 13.4 避免游戏层过重

编辑器的核心仍然是写作。花园应作为情绪反馈和长期激励存在，不应占用过多注意力。

## 14. 总结

写作花园养成小游戏的关键不是把写作变成任务，而是把写作留下的痕迹变成可照看的世界。

主花园让用户看到长期积累，文档花盆让每篇文章拥有自己的生命记录。动态资源系统避免奖励变得机械，回访奖励鼓励用户重新连接旧知识，AI 完善度判断则帮助系统识别文档生命周期，但不应替代用户的创作判断。

最终体验应当是：

> 用户每次写作、完善和回访，都能让自己的花园发生一点变化。久而久之，花园不只是奖励系统，而是用户写作生活的可视化档案。
