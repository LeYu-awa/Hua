## 一、当前多文档场景的用户痛点

通过已有功能（无限画布、花园文章、工作流、Agent）和竞品研究，梳理出以下核心痛点：

| # | 痛点 | 典型场景 | 严重程度 |
|---|---|---|---|
| 1 | **信息孤岛** | 写了10+篇笔记/文章，但彼此之间缺乏关联，知识点散落在不同文档中无法串联 | ⭐⭐⭐⭐⭐ |
| 2 | **检索低效** | 需要从大量文档中找到特定内容时，关键词搜索往往词不达意，上下文丢失 | ⭐⭐⭐⭐ |
| 3 | **跨文档洞察难** | 多篇文档中都涉及同一概念，但需要人工逐篇阅读才能提炼共性结论 | ⭐⭐⭐⭐⭐ |
| 4 | **创作接力断层** | 从灵感记录→笔记→文章的过程中，内容在不同文档间流转时信息损耗严重 | ⭐⭐⭐⭐ |
| 5 | **协作认知负担** | 多人编辑时，同一页面的不同理解容易产生分歧，缺乏自动化的共识机制 | ⭐⭐⭐ |

这些痛点恰好与项目中已有的 **AgentSystem**（事件采集/连接推荐/共识分析）和 **InfiniteCanvas**（节点化内容组织）能力方向一致，说明我们已有基础设施，缺的是产品层的最优整合。

## 二、AI 能力适配多文档场景的落地方向

### 方向 A：智能知识图谱（自动关联）
在无限画布基础上，AI 自动分析文档间的语义关联，生成知识图谱。

```
用户写笔记A（关于React Hooks）→
用户写笔记B（关于useEffect）→
AI自动检测到B是A的子概念 →
画布中B节点与A节点之间自动生成关联线 →
鼠标悬浮显示关联类型："B 继承/扩展了 A"
```

- **依赖**：现有 `useCanvasAgent` 的 `ConnectionRecommender`
- **技术可行性**：高（已实现节点关联数据模型）
- **用户价值**：极高——零操作成本获得知识结构

### 方向 B：AI 写作助手（多文档语境感知）
写作时 AI 不仅理解当前文档，还感知用户所有相关文档的上下文。

```
用户在写"闭包"相关文章 →
编辑器侧边栏自动推荐："你之前在《JavaScript基础》中写过相关片段，是否引用？" →
点击后以引用块形式嵌入 →
AI 检测到当前论述与旧内容有视角差异，建议补充
```

- **依赖**：现有 `SearchBridge` + Agent 的语义搜索
- **技术可行性**：中高（需要 RAG 索引支持）
- **用户价值**：极高——消除重复劳动，提升内容深度

### 方向 C：AI 文档总结与洞察（聚合分析）
AI 自动聚合多篇相关文档，生成综述、对比分析或趋势洞察。

```
用户选中画布上3篇关于"状态管理"的笔记 →
AI 分析3篇内容 →
生成对比表格（Redux vs Zustand vs Jotai）→
自动创建新的"综述"节点挂在画布 →
用户可一键发布到"公共花园"
```

- **依赖**：Agent 的 `ConsensusAnalyzer` + LLM 总结能力
- **技术可行性**：中（LLM 输出质量依赖 prompt 工程）
- **用户价值**：高——从碎片信息到结构化知识

### 方向 D：多文档协作 AI 助手（团队场景）
在多人协作的文档空间中，AI 充当"第三观察者"。

```
A和B同时编辑同一篇文档 →
A添加了"性能优化方案X" →
B添加了"性能优化方案Y" →
AI 检测到冲突/互补 →
自动创建对比分析卡片挂在画布 →
建议两人讨论决议
```

- **依赖**：现有 Yjs 协作 + Agent 事件流
- **技术可行性**：中高（事件采集已有，分析需要完善）
- **用户价值**：中（团队场景，当前项目偏个人）

综合评估，建议优先级：**A > B > C > D**

## 三、技术可行性分析

### 已有基础设施

```
┌─────────────────────────────────────────────┐
│ src/features/agent/                         │
│   ├── useCanvasAgent.ts     ← 画布 Agent    │
│   │   ├── EventCollector    ← 事件采集 ✅   │
│   │   ├── ConnRecommender   ← 连接推荐 ✅   │
│   │   └── ConsensusAnalyzer ← 共识分析 ✅   │
│   │                                         │
│   └── agent_tools/                          │
│       └── connection_prompt.ts  ← AI提示词  │
├─────────────────────────────────────────────┤
│ src/features/infinite-canvas/               │
│   ├── nodes/             ← 节点模型 ✅      │
│   ├── SearchBridge.ts    ← 语义搜索 ✅      │
│   └── CollabSync.ts      ← 协作同步 ✅      │
├─────────────────────────────────────────────┤
│ 已有依赖：supabase + pixi.js + yjs + openai │
└─────────────────────────────────────────────┘
```

### 关键依赖项检查

| 能力 | 所需 | 已有 | 缺口 |
|---|---|---|---|
| 语义搜索 | Supabase pgvector / OpenAI embeddings | Supabase 可用 | 需建 embedding 索引 |
| 关联推荐 | Agent ConnectionRecommender | 已有接口 | 需优化推荐算法 |
| AI 扩写 | LLM API | OpenAI 集成存在 | 需接入 API key 流程 |
| 多文档聚合 | LLM + 文档索引 | RAG 体系未建 | 需搭建知识库索引 |
| 协作感知 | Yjs event stream | Yjs 已集成 ✅ | 无缺口 |

### 推荐实施路径

```
Phase 1（短期 1-2周）→ 方向 A
  └── Agent 连接推荐全自动触发：编辑文档时 AI 自动扫描关联，画布生成关联线

Phase 2（中期 2-4周）→ 方向 B
  └── 写作时侧边栏 AI 推荐相关文档：SearchBridge 增强 + Agent 建议面板

Phase 3（中期 4-6周）→ 方向 C
  └── 多文档聚合生成综述：选中→AI 分析→综述节点

Phase 4（长期 6-8周）→ 方向 D
  └── 协作 AI 助手：事件驱动的 Awareness 分析
```

## 四、核心场景与功能规划

### 场景 1：学习时自动建立知识网络

**用户故事**：作为学习者，我在无限画布上写关于"机器学习"的笔记。AI 自动扫描我已发布的花园文章，发现我之前写过《线性代数基础》和《Python NumPy入门》，AI 自动在画布上创建这两个关联节点，并用虚线连接，标注"前置知识"。

**功能规划**：
- 文档保存/更新时 → Agent EventCollector 触发 → ConnRecommender 分析语义 → 画布生成/更新关联
- 关联类型：`前置知识` | `延伸阅读` | `观点冲突` | `补充说明`

### 场景 2：创作时 AI 辅助引用

**用户故事**：作为写作者，我在编辑器中写文章。AI 持续感知我的写作内容，当检测到某个概念我曾在其他文档中写过时，侧边栏弹出推荐卡片，点击即可嵌入引用块。

**功能规划**：
- 编辑器插件（ArticleEditorPage 集成）→ 实时语义匹配 → 推荐卡片列表
- 支持：引用原文 | 改写后引用 | AI 合并两段内容

### 场景 3：从碎片到文章的 AI 工作流

**用户故事**：我在画布上积累了20+张灵感卡片和搜索卡片。我框选其中5张相关卡片，点击"AI 整理"→ AI 自动分析这5张卡片的内容→生成结构化的文章大纲→我确认后自动创建 ArticleNode 并打开编辑器填充初稿。

**功能规划**：
- 画布多选模式 → "AI 整理"按钮 → Agent ConsensusAnalyzer 聚合 → LLM 生成大纲/初稿 → 写入新节点

## 五、产品价值主张

**一句话**：让 AI 成为用户知识网络的神经系统——自动感知、自动关联、自动沉淀。

**关键指标**：
- 关联覆盖率：用户在画布上的节点中，AI 自动建立的关联占比 > 60%
- 引用采纳率：AI 推荐的相关文档，用户采纳率 > 40%
- 整理效率：从碎片到文章的平均耗时降低 70%（对比纯手动）

**核心竞争力**：
- 不是通用 AI 写作工具，而是**扎根于用户已有知识体系**的 AI 助手
- 不是孤立聊天窗口，而是**深度嵌入无限画布 + 花园空间**的 AI
- 不是单文档 AI，而是**跨文档感知**的 AI

## 六、风险和应对

| 风险 | 可能影响 | 应对 |
|---|---|---|
| AI 关联不够精准，推荐噪音大 | 用户关闭功能 | 冷启动期只推荐高置信度关联（>85%），用户可标记"不相关"训练模型 |
| RAG 索引搭建复杂 | 进度延迟 | 初期用 Supabase `ilike` 全文搜索代替向量搜索，逐步迁移到 pgvector |
| API 成本不可控 | 运营成本高 | 限制每日 AI 调用次数 / 本地小模型跑分类，大模型只做总结生成 |
| 用户隐私顾虑（文档内容发 AI） | 用户拒绝 | 明确标注哪些功能需联网 AI，提供纯本地模式（Tauri 侧运行小模型） |
