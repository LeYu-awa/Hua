# Agent 落地待解决场景汇总

> 面向对象：Agent / Rust 后端 / AI 推理 / 协作画布 / Live2D / 回放系统开发者  
> 所属项目：花箴 / 花溯  
> 文档目的：把 Agent 需要落地的核心场景拆成可开发、可联调、可验收的任务清单。

---

## 1. 总览

花箴当前项目已经具备这些基础：

- **协作画布**：基于 `tldraw` 承载无限画布、节点、拖拽文档卡片与空间布局。
- **多人协作**：基于 `Yjs + Supabase Realtime` 同步画布状态、Presence、在线状态与协作上下文。
- **共笔 AI**：已有 DeepSeek 共笔调用、Prompt 身份、场景模板、灵感注入等方向。
- **Live2D 花灵**：规划中承担陪伴、情绪反馈、提示气泡、TTS/语音对话等交互角色。
- **Tauri 后端**：适合作为 Agent 调度器、事件流存储、规则引擎、AI API 编排和 IPC 推送层。

Agent 的落地目标不是“替用户做决定”，而是持续理解画布内容、写作行为和协作状态，在合适时机提供**温柔、不强迫、可忽略**的提示。

---

## 2. Agent 基础数据闭环

所有场景都依赖同一条基础链路：

```text
前端操作事件
  -> 事件标准化
  -> Rust Agent 调度器
  -> SQLite / 本地事件流存储
  -> 规则引擎 / Embedding / LLM / RAG
  -> IPC 推送 UI 指令
  -> 画布提示 / Live2D 动作 / 回放标记 / 复盘报告
```

### 2.1 待统一的数据类型

| 数据类型 | 来源 | 关键字段 | 用途 |
| --- | --- | --- | --- |
| 画布节点 | tldraw shape / 文档卡片 | nodeId、text、x、y、w、h、authorId、createdAt、updatedAt | 语义分析、空间聚类、隐含连接 |
| 画布连线 | tldraw binding / connector | fromNodeId、toNodeId、type、createdBy | 判断用户显式关系 |
| 操作事件 | 编辑器 / 画布 / 输入框 | eventId、userId、type、payload、timestamp | 回放、情绪、写作节奏 |
| 协作状态 | Yjs Awareness / Presence | userId、cursor、selectedNodeIds、activeArea、online | 多人感知、接力追踪 |
| 聊天消息 | Supabase collab_messages | senderId、content、createdAt、docId | 语义补充、争议判断 |
| AI 输出 | Agent / CoWrite / Live2D | trigger、prompt、result、accepted、dismissed | 评估干预有效性 |
| 用户档案 | SQLite / Vector DB | baseline、writingStyle、topicVector、historyStats | 个性化阈值和历史对比 |

## 3. 场景一：隐含连接推荐

### 场景描述

多人协作时，用户 A 在画布左上方写：

> 用户调研数据显示 80% 用户需要实时同步

用户 B 在右下方写：

> 实时同步功能开发排期约 3 周

两者语义高度相关，但位置相距甚远，用户可能没有察觉其中联系。Agent 需要主动推荐一条“可忽略的弱连接”。

### 数据流转

```text
1. 调度器监听画布事件流，捕获两个新建节点事件。
2. 提取节点文本、作者、坐标、创建时间、节点 ID。
3. 调用 Embedding API：节点 A -> 向量 a，节点 B -> 向量 b。
4. 计算余弦相似度，得到 similarity = 0.87。
5. 从节点元数据读取坐标，计算空间距离 distance = 700px。
6. 规则引擎判断：similarity > 0.7 且 distance > 100px。
7. 检查是否已存在显式连线，避免重复提醒。
8. 调用 LLM 生成温柔、不强迫的提示语。
9. 通过 IPC 推送给前端：虚线连接、提示气泡、候选连线节点 ID。
10. 同步触发 Live2D“发现连接”动画和对话气泡。
```

### 输出结果

- 画布显示两节点之间的**淡色虚线连接**。
- 节点旁出现提示气泡：

```text
这两条好像都在聊“实时同步”，要不要先轻轻连起来看看？
```

- 用户可选择：接受连线 / 暂时忽略 / 不再提示此类关系。
- Live2D 花灵播放“探头发现”动画，并显示同样文案。

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| Embedding / 向量嵌入 | 将节点文本转为向量，使机器理解节点含义 |
| Semantic Similarity / 语义相似度 | 判断两个节点是否讨论同一主题 |
| Cosine Similarity / 余弦相似度 | 用向量夹角余弦值量化相似度 |
| Rule-based System / 规则系统 | 用“相似度阈值 + 空间距离阈值 + 去重规则”保证触发确定性 |
| LLM / 大语言模型 | 把结构化判断转成自然语言提示 |
| Prompt Engineering / 提示词工程 | 约束语气为“温柔、不强迫、不打断” |
| IPC / 进程间通信 | 将分析结果从 Rust Agent 推送到 React UI |
| Live2D Feedback | 把洞察通过花灵动作和气泡表达出来 |

### 待解决问题

- 如何从 tldraw shape 中稳定提取纯文本内容。
- 如何区分“语义相关”与“重复内容”。
- 如何避免同一组节点反复提示。
- 用户接受或忽略后，是否要写入偏好学习。
- Embedding 调用频率和本地缓存策略。

## 4. 场景二：语义空白区识别

### 场景描述

产品团队在画布上写下 20 多个节点，其中 10 个集中在技术实现方案，6 个在成本估算，4 个在排期计划，但完全没有涉及用户体验。Agent 需要识别“缺失的讨论视角”。

### 数据流转

```text
1. 调度器检测到画布连续 10 分钟无新增节点，判定为稳定状态。
2. 触发一次全量语义分析。
3. 批量提取画布全部节点文本。
4. 调用 Embedding API，生成节点向量集合。
5. 将节点映射到语义空间，执行聚类和主题分布统计。
6. 对预设视角库进行语义检索：用户接受度、用户操作流程、用户体验反馈、风险、商业价值等。
7. 发现“用户侧体验”相关区域覆盖度为 0 或极低。
8. 规则引擎标记为语义空白区。
9. 调用 LLM 生成建设性提醒和待补充视角清单。
10. 前端显示浮动提示框和可点击的“待补充视角”。
11. Live2D 同步提示，点击后可生成占位节点。
```

### 输出结果

- 画布空白区域显示提示：

```text
现在技术和排期聊得很清楚了，好像还可以补一小块“用户怎么感受这个功能”。
```

- 待补充视角清单：
  - 用户接受度
  - 用户操作流程
  - 用户体验反馈
- 用户点击后生成半透明占位节点模板。

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| Embedding / 向量嵌入 | 将所有节点批量转成向量 |
| Semantic Space / 语义空间 | 把画布内容映射成可计算的主题分布 |
| Vector Density / 向量密度 | 判断某些语义区域是否无人覆盖 |
| Semantic Search / 语义检索 | 用预设问题视角检索画布中是否已有覆盖内容 |
| Rule-based System / 规则系统 | 控制“稳定状态后才分析”的触发时机 |
| LLM / 大语言模型 | 生成不批评、不否定用户的提醒 |
| Prompt Engineering / 提示词工程 | 限定输出为“建设性、不指责” |
| Intervention Timing / 干预时机 | 选择画布稳定后触发，避免实时打扰 |

### 待解决问题

- 需要建立项目内“视角库”：用户、技术、成本、排期、风险、商业、情绪、角色关系等。
- 如何判断一个视角“完全缺失”还是“覆盖不足”。
- 占位节点生成在画布哪个位置更自然。
- 团队协作中谁有权限接受 Agent 建议。

## 5. 场景三：共识 / 分歧检测

### 场景描述

四人在画布上讨论“新功能是否应该上云”：

- 用户 A：应该上云，弹性扩展对业务高峰期很重要。
- 用户 B：上云成本太高，现有服务器足够。
- 用户 C：可以混合云，核心数据本地，计算弹性上云。
- 用户 A：上云后运维压力会小很多。
- 用户 D：同意 A，上云是趋势。

Agent 需要判断当前讨论是走向共识，还是分歧扩大，并找出可能的共识桥梁。

### 数据流转

```text
1. 调度器通过关键词和空间邻近性检测到“上云”议题簇。
2. 提取议题簇内所有节点文本、作者、时间、位置。
3. 批量调用 Embedding API。
4. 两两计算余弦相似度，形成相似度矩阵。
5. 规则引擎初步标记：相似度 > 0.85 为共识组，< 0.55 为偏离组，中间值为中间派。
6. 调用 LLM 分析：观点是对立、互补、补充还是折中。
7. LLM 判断：A/A2/D 为支持上云，B 为反对上云，C 为混合云折中方案。
8. 解析结果：当前状态为“分歧加大”，C 是潜在共识桥梁。
9. 通过 IPC 推送可视化指令：颜色光圈、争议连线、争议面板。
10. Live2D 以中立语气促进沟通。
```

### 输出结果

- 画布可视化：
  - 绿色光圈：共识组。
  - 红色光圈：异议者。
  - 黄色光圈：中间派 / 桥梁方案。
  - 红色虚线：争议双方。
- 争议面板显示：

```text
当前争议：是否上云
支持：3 人
反对：1 人
折中方案：1 人提出混合云
```

- Live2D 提示：

```text
好像大家在“上云”这件事上有不同看法，C 的混合云方案要不要再聊聊？
```

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| Embedding / 向量嵌入 | 计算议题簇内观点文本的语义距离 |
| Cosine Similarity / 余弦相似度 | 构建相似度矩阵，发现观点分组 |
| Social Network Analysis / 社交网络分析 | 识别支持组、反对组、中间派结构 |
| LLM / 大语言模型 | 判断语义距离背后的关系：对立、补充、折中 |
| Reasoning / 推理 | 输出讨论阶段和桥梁观点 |
| Grounding / 共识建立 | 帮助团队显性化当前共识状态 |
| Awareness / 协作感知 | 让所有参与者意识到当前讨论结构 |
| Role Identification / 角色识别 | 标记 C 为潜在共识桥梁 |
| Collaboration Visualization / 协作可视化 | 用光圈、连线、面板呈现群体结构 |
| Intervention Timing / 干预时机 | 等议题节点足够密集后再触发 |

### 待解决问题

- 如何定义“议题簇”：关键词、空间距离、时间窗口如何组合。
- 需要避免把正常补充误判成分歧。
- 争议面板是否默认显示，还是仅在用户点击后展开。
- Live2D 文案必须中立，不能站队或评价对错。

## 6. 场景四：情绪推断 + 主动干预

### 场景描述

用户连续写作 15 分钟，删除 / 输入比达到 3.17，撤销 6 次，窗口切换 8 次，最长停顿 45 秒，光标在多个词之间反复修改。Agent 需要判断用户是否卡住、焦虑或分心，并决定是否温柔干预。

### 数据流转

```text
1. 调度器持续接收键盘输入、删除、撤销、窗口切换、光标停留等操作事件。
2. 使用 5 分钟滑动窗口滚动统计行为指标。
3. 与个人基线对比：删除/输入比、撤销频次、窗口切换次数、长停顿次数。
4. 规则引擎标记异常信号：焦虑、分心、卡顿。
5. 按权重计算焦虑指数：删改率 30%、撤销率 30%、窗口切换 20%、停顿 20%。
6. 当前焦虑指数 = 3.73，超过基线 3 倍。
7. 检查干预冷却机制，确认距上次干预超过 30 分钟。
8. 调用 LLM 生成 20 字以内的关怀语。
9. 通过 IPC 触发 Live2D“关心”动画和对话气泡。
10. UI 边缘显示微弱呼吸光晕，点击 Live2D 展开轻量帮助面板。
```

### 输出结果

- Live2D 显示：

```text
卡在这里了？要不要先写别的段落。
```

- 帮助面板提供：
  - 先跳过这一段
  - 让 AI 帮我列 3 个小标题
  - 进入 5 分钟专注模式
  - 不再提醒

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| Affective Computing / 情感计算 | 从删改、撤销、停顿、切换中推断情绪状态 |
| Anomaly Detection / 异常检测 | 判断当前行为是否显著偏离个人基线 |
| Behavior Modeling / 行为建模 | 将操作序列转成行为特征向量 |
| Rule-based System / 规则系统 | 用确定性规则判断异常信号和是否干预 |
| Sliding Window / 滑动窗口 | 以近 5 分钟为统计窗口，保证时效性 |
| Baseline / 个人基线 | 让阈值因人而异，而不是固定死值 |
| Intervention Timing / 干预时机 | 用冷却机制避免反复打扰 |
| LLM / 大语言模型 | 将行为摘要转成自然、不监视感的关怀语 |
| Prompt Engineering / 提示词工程 | 约束文案“温柔不油腻、具体可操作” |
| User Profiling / 用户画像 | 长期学习用户写作习惯和触发偏好 |

### 待解决问题

- 当前项目需要先补齐操作流采集和 SQLite 存储。
- 需要明确隐私策略：这些行为分析只在本地算，或是否上传。
- 不要直接说“我检测到你焦虑”，要说“好像有点卡住”。
- 用户关闭提醒后，应写入偏好和冷却策略。

## 7. 场景五：AI 复盘报告生成

### 场景描述

用户完成一篇约 3000 字的技术文档，持续写作 2 小时 15 分钟，希望看到一份有洞察的复盘报告，了解写作模式、进步空间和历史对比。

### 数据流转

```text
1. 用户点击“生成复盘报告”，或 Agent 检测到 15 分钟无输入且字数达标。
2. 从 SQLite 加载本次写作完整操作流。
3. 统计计算器生成结构化指标：总时长、净输出、总输入、删改率、撤销、停顿、流畅度曲线。
4. 提取最长流畅期、最长卡顿点、高频修改区、高光段落。
5. 将本次文档整体内容转为 User Embedding。
6. 在历史向量库中检索同类文档作为对比基线。
7. 调用 LLM 生成叙事性报告。
8. 前端用 Streaming 方式逐字展示报告。
9. 报告页渲染流畅度曲线、修改热力图、高光/卡顿节点。
10. 后台更新用户档案：删改率趋势、心流时长、常见卡点、最佳写作时段。
```

### 输出结果

报告包括：

- 本次写作概览。
- 3-5 条关键洞察。
- 流畅期 / 卡顿点 / 高频修改区。
- 与历史同类文档对比。
- 下一次写作建议。

示例语气：

```text
这次你在“方案展开”阶段进入状态很快，最长连续 23 分钟几乎没有删改。相比之前同类文档，删改率从 61% 降到 52%，说明你对结构的把握更稳定了。
```

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| RAG / 检索增强生成 | 检索历史同类文档，再生成个性化报告 |
| Vector Database / 向量数据库 | 存储历史文档向量和写作统计 |
| User Embedding / 用户向量 | 表示本次文档主题指纹 |
| User Profiling / 用户画像 | 形成长期写作风格和行为趋势 |
| LLM / 大语言模型 | 把结构化数据转成有温度的复盘叙事 |
| Prompt Engineering / 提示词工程 | 将 Agent 定位为“不评价好坏的写作教练” |
| Streaming / 流式输出 | 报告边生成边显示 |
| Reflection / 反思 | 帮助用户建立元认知 |
| Insight Extraction / 洞察提取 | 只筛选最值得知道的重点，而非罗列数据 |

### 待解决问题

- 复盘报告是否只本地保存，是否参与用户长期画像。
- 哪些指标适合展示，哪些只用于内部计算。
- 如何避免报告显得“审判式”。
- 需要复用或扩展现有 `HeatmapView`、`InkPlaybackPage` 能力。

## 8. 场景六：多人接力写作追踪

### 场景描述

三人团队在 2 小时内协作撰写项目复盘报告：C 先搭建框架，A 和 B 分别在不同区域创作，之后 A 和 B 在“方案”区进行了两轮接力编辑。Agent 需要追踪协作过程并输出洞察。

### 数据流转

```text
1. 调度器持续记录三人操作事件。
2. 将每个用户当前编辑节点映射到画布区域：背景、问题、方案、结果、教训。
3. 生成用户时间线轨迹。
4. 通过 Sequence Modeling 检测接力模式：A 是否在 B 离开后进入同一区域并延续其内容。
5. 检测并行协作模式：多人是否同时工作在不同区域，但内容语义相关。
6. 标记显式沟通和隐式协作：聊天、评论、引用、内容承接。
7. 调用 LLM 生成 2-3 句协作洞察。
8. UI 渲染用户路径轨迹、金色接力点、协作面板、角色标签。
9. 回放系统进度条标记接力点和并行协作时段。
```

### 输出结果

- 画布显示：
  - A 蓝色轨迹线。
  - B 绿色轨迹线。
  - 金色圆点标记接力点。
- 协作面板显示：

```text
C 先搭建了整体框架；A 和 B 在“方案”区形成两轮接力；B 的结果段落与 A 的方案段落形成了明显呼应，但中间没有显式沟通。
```

- 用户头像旁显示角色标签：
  - C · 框架设计者
  - A · 内容贡献者
  - B · 深化者

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| CSCW / 计算机支持的协同工作 | 分析多人如何在共享空间中协作 |
| Sequence Modeling / 序列建模 | 对齐多人操作时间线，识别先后关系 |
| Turn-taking / 轮流发言 | 检测 A/B 在同一区域的接力编辑 |
| Awareness / 协作感知 | 让团队知道谁在哪个区域工作 |
| Social Network Analysis / 社交网络分析 | 从接力关系和内容耦合中识别角色结构 |
| Role Identification / 角色识别 | 自动生成框架者、深化者、贡献者等标签 |
| Grounding / 共识建立 | 追踪团队如何通过接力形成共同理解 |
| LLM / 大语言模型 | 将协作轨迹抽象为叙事洞察 |
| Collaboration Visualization / 协作可视化 | 用轨迹、接力点、角色标签呈现协作模式 |

### 待解决问题

- 如何把 tldraw 无限画布划分为稳定语义区域。
- 角色标签是否允许用户编辑或关闭。
- 接力判断需要结合时间、空间、语义和引用关系，不能只看位置。
- 回放系统需要支持事件级时间轴和可视化标记。

## 9. 项目补充场景七：画布文档卡片智能归档

### 场景描述

当前画布支持把协作文档拖到画布上形成文档卡片。随着卡片变多，用户可能把需求、草稿、资料、复盘、灵感卡片混在一起。Agent 需要自动识别卡片类型，并建议分组或归档。

### 数据流转

```text
1. 用户拖入或创建文档卡片。
2. Agent 提取卡片标题、正文摘要、所在位置、周边节点。
3. 对标题和正文摘要调用 Embedding API。
4. 与项目内分类标签库比较：需求、资料、草稿、复盘、灵感、待办、人物设定、世界观设定。
5. 规则引擎判断是否需要推荐分组。
6. LLM 生成分组建议文案。
7. UI 在卡片边缘显示轻量标签建议，用户一键接受。
```

### 输出结果

```text
这几张好像都属于“资料引用”，要不要先收成一个小组？
```

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| Embedding | 判断文档卡片主题 |
| Semantic Classification | 给卡片打语义标签 |
| Rule-based System | 判断何时推荐分组 |
| LLM | 生成自然的归档建议 |
| IPC | 推送标签、分组建议到画布 UI |

### 待解决问题

- 需要从文档卡片追溯原始协作文档内容。
- 标签接受后是否写回文档元数据。
- 是否支持用户自定义标签体系。

## 10. 项目补充场景八：共笔 AI 与画布上下文联动

### 场景描述

项目已有共笔模式和画布模式。用户在画布上梳理了人物设定、情节节点、技术方案或写作大纲，再进入共笔时，Agent 应该能把画布上下文注入共笔 Prompt，而不是让 AI 只看当前文本。

### 数据流转

```text
1. 用户在共笔页面点击“基于画布续写”或进入空会话。
2. Agent 读取当前 conversationId 关联画布中的节点、文档卡片和选中区域。
3. 对画布内容做摘要和主题排序。
4. 检索与当前共笔会话最相关的 5-8 个节点。
5. 组装上下文：当前文本 + 相关画布节点 + AI 身份 + 场景模板。
6. 调用现有 DeepSeek 共笔接口。
7. 生成内容后记录引用来源，便于用户知道 AI 借用了哪些画布信息。
```

### 输出结果

- 共笔侧边栏显示“已参考画布节点”：
  - 人物关系：A 与 B 的冲突
  - 场景设定：雨夜车站
  - 主题：离别后的重逢
- AI 输出更贴合当前画布设定。

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| RAG | 从画布节点中检索与当前写作相关的上下文 |
| Embedding | 计算当前段落与画布节点的语义相关性 |
| Prompt Engineering | 把画布上下文安全注入共笔 Prompt |
| LLM | 基于共笔身份和上下文生成续写 |
| Grounding | 保证 AI 输出能追溯到画布设定 |

### 待解决问题

- 如何避免 Prompt 过长。
- 是否默认注入全部画布，还是只注入用户选中区域。
- AI 输出引用来源如何展示得不打扰。
- 需要与现有 `src/features/cowrite` 的 Prompt 构建逻辑对接。

## 11. 项目补充场景九：协作聊天与画布节点互相引用

### 场景描述

项目已有右侧聊天栏和协作画布。多人讨论时，很多关键决策可能发生在聊天里，而不是画布节点里。Agent 需要识别聊天消息和画布节点之间的关系，推荐把重要聊天沉淀成画布节点。

### 数据流转

```text
1. Agent 监听 Supabase Realtime 聊天消息。
2. 对聊天消息进行轻量分类：闲聊、决策、问题、风险、待办、引用画布。
3. 对“决策/待办/风险”类消息生成 Embedding。
4. 与画布节点进行语义匹配。
5. 如果聊天内容重要但画布无对应节点，触发沉淀建议。
6. 用户点击接受后，在画布合适位置生成节点，并附带来源消息链接。
```

### 输出结果

```text
刚才聊天里定下了“先做实时同步 MVP”，要不要把它放到画布上？
```

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| Semantic Classification | 判断聊天消息类型 |
| Embedding | 匹配聊天和画布节点 |
| Rule-based System | 仅对决策、待办、风险类消息触发 |
| LLM | 把聊天内容压缩成节点文案 |
| Collaboration Visualization | 在画布上标记“来自聊天”的节点 |

### 待解决问题

- 需要定义聊天消息是否可被 Agent 分析的隐私边界。
- 生成节点时应避免暴露私人表达，只保留协作结论。
- 节点来源需要可追溯，但不应打断协作体验。

## 12. 项目补充场景十：Live2D 花灵状态机与 Agent 信号统一

### 场景描述

项目规划中 Live2D 花灵会根据写作状态反馈动画情绪。Agent 需要把不同场景的信号统一映射成花灵状态，避免多个模块同时触发动画导致混乱。

### 数据流转

```text
1. 各 Agent 场景产生信号：发现连接、用户卡住、协作分歧、好友来访、收到消息、完成写作。
2. 信号进入 Live2D 状态机队列。
3. 状态机按优先级、冷却时间、用户偏好做调度。
4. 输出统一动作：mood、animation、bubbleText、ttsText、duration。
5. 前端 Live2D 模块执行动作，并回传用户是否点击/关闭。
6. Agent 根据反馈调整后续干预频率。
```

### 输出结果

| Agent 信号 | 花灵 mood | 动作 | 示例文案 |
| --- | --- | --- | --- |
| 发现隐含连接 | curious | 探头 / 指向 | 这两块好像有点关系 |
| 用户卡住 | worried | 歪头 / 轻声 | 先换一段写也可以 |
| 协作分歧 | neutral | 旁观 / 提醒 | 要不要看看折中方案 |
| 完成写作 | happy | 开花 / 跳跃 | 今天写得很完整呢 |
| 好友来访 | excited | 挥手 | 有朋友加入啦 |

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| Behavior Modeling | 把不同 Agent 信号归一成状态输入 |
| Rule-based System | 管理优先级、冷却、互斥和降噪 |
| Prompt Engineering | 控制花灵文案风格统一 |
| IPC | 从 Rust Agent 推送到 Live2D 前端模块 |
| User Profiling | 根据用户反馈调整出现频率 |

### 待解决问题

- Live2D 动作优先级表需要先确定。
- 多个 Agent 同时触发时需要队列和合并策略。
- 文案、TTS、动作三者要保持一致，不要割裂。
- 需要保留 CSS/Lottie 低成本替代方案，方便先落地。

## 13. 项目补充场景十一：墨迹回放中的 AI 关键帧标注

### 场景描述

项目已有墨迹回放方向。用户回放 2 小时协作过程时，如果只是线性播放，很难发现关键节点。Agent 需要自动在回放时间轴上标记“转折点、卡顿点、接力点、共识点、分歧点”。

### 数据流转

```text
1. 回放引擎从 SQLite 加载事件流。
2. Agent 按时间窗口聚合事件。
3. 规则引擎先检测确定性关键帧：长停顿、高频删改、多人同时编辑、节点大量新增。
4. Embedding / LLM 分析语义关键帧：主题切换、分歧出现、共识形成、方案收敛。
5. 生成回放标记：time、type、title、summary、relatedNodeIds。
6. 前端在进度条上渲染不同颜色的关键帧标记。
7. 用户点击标记后跳转到对应画布状态。
```

### 输出结果

- 回放时间轴出现标记：
  - 09:30 框架完成
  - 09:42 A 接力 B 的方案区
  - 10:05 出现上云争议
  - 10:18 混合云方案形成折中
- 用户可按关键帧回看，而不是从头拖动。

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| Sequence Modeling | 从事件序列中识别阶段变化 |
| Anomaly Detection | 找出异常停顿、密集修改、突然切换 |
| LLM | 给关键帧生成简短标题和摘要 |
| Insight Extraction | 从大量事件中筛选真正重要的节点 |
| Collaboration Visualization | 在回放条和画布上同步展示关键帧 |

### 待解决问题

- 事件流必须足够完整，才能还原画布状态。
- 关键帧数量需要控制，避免时间轴过载。
- AI 标记应允许用户删除、重命名、收藏。

## 14. 项目补充场景十二：跨项目写作习惯与最佳时段推荐

### 场景描述

花箴强调长期陪伴。Agent 不应只看单次写作，而应跨项目观察用户的写作习惯，例如：晚上更容易进入心流、技术文档常卡在架构分层、小说创作常在人物对话处删改多。然后在合适时间给出轻量推荐。

### 数据流转

```text
1. 每次写作结束后，将统计摘要写入用户档案。
2. 将文档主题、写作类型和行为特征转为向量或结构化记录。
3. 定期计算趋势：最佳时段、常见卡点、删改率变化、心流时长变化。
4. 当用户新建类似项目时，检索历史同类项目。
5. Agent 生成个性化提醒或默认工作流建议。
```

### 输出结果

```text
你之前写架构类文档时，先列模块边界会更顺。要不要这次也先生成一个分层占位？
```

### 技术方案说明

| 技术术语 | 在本场景中的具体作用 |
| --- | --- |
| User Profiling | 形成长期写作习惯画像 |
| Vector Database | 存储历史项目向量和统计数据 |
| RAG | 新项目启动时检索历史相似项目 |
| Baseline | 动态更新用户个人正常状态 |
| LLM | 把历史规律转成自然建议 |

### 待解决问题

- 用户画像需要有明确开关和数据删除能力。
- 推荐频率要非常克制。
- 需要区分“帮助用户”与“评价用户”。

## 16. 推荐落地优先级

### Phase 1：先把数据跑通

| P0 | IPC 指令协议 | Agent 必须能把结果推回 UI 和 Live2D |
| P1 | 回放关键帧数据结构 | 后续复盘、接力、卡顿都能复用 |

### Phase 2：做低风险高感知智能

| 优先级 | 能力 | 原因 |
| --- | --- | --- |
| P1 | 停顿检测 + Live2D 温柔提示 | 不依赖复杂 AI，最容易产生陪伴感 |
| P1 | 隐含连接推荐 | 与无限画布高度契合，用户感知强 |
| P1 | 聊天沉淀成画布节点 | 贴合现有多人协作和右侧聊天栏 |
| P2 | 画布文档卡片智能归档 | 能改善画布变乱的问题 |

### Phase 3：做协作智能和复盘

| 优先级 | 能力 | 原因 |
| --- | --- | --- |
| P2 | 多人接力追踪 | 体现花溯“理解协作过程”的差异化 |
| P2 | 共识 / 分歧检测 | 适合团队评审、方案讨论、共创场景 |
| P2 | AI 复盘报告 | 能把事件流价值显性化 |
| P3 | 跨项目用户画像 | 长期陪伴能力，但需要隐私和数据策略成熟 |

```ts
      type: "live2d_signal";
      mood: "happy" | "neutral" | "sleepy" | "excited" | "worried" | "curious";
      animation: string;
      bubbleText: string;
      priority: number;
    }
  | {
      type: "replay_marker";
      time: number;
      markerType: "handoff" | "conflict" | "flow" | "stuck" | "consensus";
      title: string;
      summary: string;
    };
```

## 18. 验收口径

Agent 场景落地时建议统一用以下标准验收：

- **可观察**：前端能看到明确结果，如虚线、气泡、面板、回放标记、Live2D 动作。
- **可忽略**：所有建议都允许关闭、忽略、不再提示。
- **可追溯**：每条 AI 建议能追溯到触发节点、事件或聊天消息。
- **可降级**：Embedding / LLM 不可用时，规则引擎和本地统计仍可工作。
- **不打扰**：有冷却时间、触发阈值、优先级队列。
- **不评价用户**：文案避免“你焦虑了”“你遗漏了”等审判式表达。
- **能复用**：事件流、规则引擎、LLM 调度、Live2D 状态机不要为单场景写死。

## 19. 最小 MVP 建议

如果先做一个可演示版本，建议只做这 5 件事：

1. **事件流采集**：记录画布节点新增、文本变化、坐标变化、用户 ID、时间戳。
2. **停顿检测**：用户停顿超过阈值后，Live2D 温柔提示。
3. **隐含连接推荐**：两个远距离节点语义相似时，画布画虚线并弹出建议。
4. **聊天沉淀节点**：聊天中出现决策或待办时，建议一键生成画布节点。
5. **回放关键帧**：在回放时间轴标记停顿、接力、节点爆发增长。

这 5 件事能覆盖：

- 事件流
- 画布分析
- 规则引擎
- Embedding
- LLM 文案
- IPC UI 指令
- Live2D 反馈
- 回放系统

也最能体现花箴 / 花溯 Agent 的产品差异化：

> 它不是一个聊天框，而是一个能理解创作过程、协作关系和用户状态的写作伙伴。
